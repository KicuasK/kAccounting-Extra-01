# AR/AP API — 2026-10-23

Implemented explicit annotations of existing posted journal lines. This does not
post a journal entry, change a financial balance, create accounts or auto-allocate
historical transactions. Policies are recorded in `VERSION01_DECISIONS.md`.

## Shared boundaries

All IDs and integer amounts are canonical decimal **strings**, including values
above JavaScript's safe-integer range. Amounts must be positive signed-64-bit
integers. Mutation payloads reject unknown fields. The existing localhost write
router requires exact Host/Origin, while selected-book runtime commands also
require the current selection-generation header. Reads are `no-store`.

The UI obtains existing permanent line IDs from
`GET /api/journal/posted/{entry_id}`. Drafts, reversal entries and already reversed
entries cannot establish or settle open items. Historical adoption is explicit;
the subledger does not claim complete coverage of an account.

## Read current state

`GET /api/open-items` returns one SQLite snapshot:

```json
{
  "coverage": "explicit-lines-only",
  "items": [{
    "id": "1", "source_line_id": "12", "source_entry_id": "6",
    "account_id": "3", "kind": "receivable", "entry_date": "2026-10-23",
    "amount_minor": "1000", "description": "款項",
    "counterparty": null, "due_date": null,
    "paid_minor": "400", "adjusted_minor": "0",
    "outstanding_minor": "600", "reversed": false
  }],
  "allocations": [{
    "id": "1", "settlement_line_id": "16", "settlement_entry_id": "8",
    "entry_date": "2026-10-24", "item_id": "1", "amount_minor": "400",
    "kind": "payment", "created_at": "2026-10-24T00:00:00.000Z",
    "void_reason": null, "voided_at": null
  }]
}
```

`kind` on an item is `receivable` or `payable`. An allocation kind is `payment`
or `adjustment`. Voided allocations remain in history, with their reason/time;
they no longer reduce outstanding or consume settlement-line capacity. Reversed
source items remain visible with `reversed: true` and zero outstanding.

`GET /api/open-items/lines/{line_id}/capacity` returns
`{"remaining_minor":"600"}`. This is the posted line amount less all effective
allocations. It does not assert the line is eligible for every item; allocation
still validates account, side, date and outstanding inside its write transaction.

## Register a complete source-line split

`POST /api/open-items`:

```json
{
  "source_line_id": "12",
  "kind": "receivable",
  "items": [{
    "amount_minor": "1000", "description": "款項",
    "counterparty": "對象", "due_date": "2026-11-01"
  }]
}
```

Returns **201** `{"item_ids":["1"]}`. An AR source is an asset debit; AP is a
liability credit. The 1–100 item amounts must equal the entire source line. A line
can be registered once. Description is required (up to 1000 characters);
counterparty is optional/null (up to 200 characters), due date optional/null and
must be a real `YYYY-MM-DD` date. Supplied text is trimmed and cannot contain NUL.
There is no required account name, new-account rule or automatic account setup.

Source splits and item metadata are immutable in this slice. There is no item
edit/delete endpoint. An ordinary correcting entry remains separate history.

## Allocate partial or complete receipt/payment

`POST /api/open-items/allocations`:

```json
{
  "settlement_line_id": "16",
  "allocations": [
    {"item_id":"1","amount_minor":"400","kind":"payment"}
  ]
}
```

Returns **201** `{"allocation_ids":["1"]}`. Each request has 1–100 allocations.
The settlement line must be posted, use the same account with opposite side and
have a date no earlier than the source. Each allocation is limited by both item
outstanding and cumulative settlement-line capacity. One line may be partially
allocated across multiple requests. Repeated item IDs in one request share the
same capacity; they do not bypass the cumulative limit.

Validation and all writes/audit records use `BEGIN IMMEDIATE`. A failed member
rolls back the whole request. No FIFO or inferred write-off account is applied.

## Explicitly cancel an allocation

`POST /api/open-items/allocations/{allocation_id}/void`:

```json
{"reason":"重新核對後改配其他款項"}
```

Returns **200** `{"voided":true}`. Reason is required, trimmed and up to 1000
characters. Cancelling an already cancelled or missing allocation returns 409.
Cancellation appends an immutable record and audit event. The original payment
and its posted journal remain intact. To reverse a source or settlement entry,
first explicitly cancel every effective allocation that depends on it; both the
repository and SQLite posting trigger enforce this dependency.

## Error contract

| HTTP | Code | Meaning |
|---|---|---|
| 400 | `open_item_invalid` | Invalid fields, IDs, JSON, text or date |
| 404 | `open_item_not_found` | Missing item/line or source is not posted |
| 409 | `open_item_reversed` | Reversed entry or a reversal entry |
| 409 | `open_item_wrong_account` | Wrong account, category or side |
| 409 | `open_item_exists` | Source line already registered |
| 409 | `open_item_split_mismatch` | Item total differs from source amount |
| 409 | `open_item_overallocated` | Item or line capacity exceeded |
| 409 | `open_item_date_order` | Receipt/payment predates source |
| 409 | `open_item_allocation_inactive` | Missing or cancelled allocation |
| 409 | `open_item_allocations_active` | Journal reversal has effective allocations |
| 422 | `open_item_overflow` | Exact arithmetic exceeds integer capacity |

Corrupt stored data and database failures use the existing generic internal error
response. Existing origin, generation and route errors remain unchanged.
